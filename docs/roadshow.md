## 一、解决了谁的什么问题？

### 目标用户
**面向所有行业的面试者**（包括技术、产品、运营、设计等各岗位求职者）

### 用户痛点

| 痛点 | 描述 |
|------|------|
| 盲目准备 | 不知道面试官会问什么问题 |
| 准备不充分 | 简历上的项目经历被问到细节时答不上来 |
| 缺乏针对性 | 通用面试题无法覆盖个人项目亮点 |

### 解决方案
**上传项目描述 + 技术栈 → AI自动生成刁钻技术追问**

## 三、ADR-1：AI追问生成采用同步调用

### 背景
系统需要根据用户输入的项目描述实时生成技术追问，这是核心业务流程。

### 选项对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| **方案A：同步调用** | 即时反馈、实现简单、交互性好 | 响应延迟、并发受限 |
| **方案B：异步调用** | 高并发友好、资源占用低 | 实现复杂、需要WebSocket |

### 决策
选择 **方案A：同步调用**

### 理由
1. **用户体验优先**：面试场景需要即时反馈，用户期望立即看到追问结果
2. **交互性要求**：多轮面试需要根据前一个回答生成下一个问题
3. **实现复杂度**：同步调用代码量少，维护成本低
4. **已有保护机制**：配合20秒Timeout + 降级方案，保证服务可用性

### 代价
- 响应延迟：用户需等待5-15秒
- 并发限制：需要限流保护
- 降级依赖：必须依赖预设问题库

## 四、核心工作流图

```mermaid
sequenceDiagram
    participant 用户 as 用户
    participant 面试服务 as 面试服务
    participant LLM as DeepSeek API
    participant 降级 as 预设问题库
    participant 数据库 as 数据库

    用户->>面试服务: 输入岗位+项目描述
    Note over 面试服务: 【代码锁死】参数校验
    面试服务->>面试服务: 参数验证（必填项检查）
    
    alt LLM调用成功
        面试服务->>LLM: 调用DeepSeek API
        Note over LLM: 【LLM判断】生成追问
        LLM-->>面试服务: 返回问题JSON
    else LLM超时/失败
        面试服务->>降级: 使用预设问题库
        Note over 降级: 【代码锁死】按技术栈匹配
        降级-->>面试服务: 返回预设问题
    end
    
    Note over 面试服务: 【代码锁死】格式标准化
    面试服务->>面试服务: 统一输出格式
    
    面试服务->>数据库: 保存追问记录
    面试服务-->>用户: 返回追问结果
```

**代码锁死 vs LLM判断**：

| 步骤 | 类型 | 说明 |
|------|------|------|
| 参数校验 | 代码锁死 | 固定逻辑：检查必填项、格式验证 |
| 问题生成 | LLM判断 | 动态生成：根据项目描述生成刁钻问题 |
| 降级匹配 | 代码锁死 | 固定逻辑：按技术栈分类匹配预设问题 |
| 格式标准化 | 代码锁死 | 固定逻辑：统一输出格式 |
| 记录保存 | 代码锁死 | 固定逻辑：写入数据库 |

## 六、系统最脆弱的地方及修复方案

### 最脆弱点：LLM API依赖

**风险描述**：
- DeepSeek API服务不可用 → 系统降级到预设问题库
- API响应时间过长 → 用户体验下降
- API调用费用不可控 → 成本风险

### 修复方案

| 措施 | 说明 |
|------|------|
| **多级缓存** | 缓存高频项目的追问结果，减少API调用 |
| **流量控制** | 限制单用户调用频率（如每分钟3次） |
| **成本监控** | 设置API调用额度告警 |
| **多LLM支持** | 支持切换不同LLM提供商（DeepSeek、OpenAI等） |
| **离线模式** | 完全离线时使用本地预设问题库 |

### 优先级排序

1. **高优先级**：多级缓存 + 流量控制
2. **中优先级**：多LLM支持
3. **低优先级**：成本监控 + 离线模式
